# iM 이룸 — UI 디자인 기준

최종 갱신: 2026-09-20

## 1. 제품 인상

iM 이룸은 내부 계산 과정을 전시하는 대시보드가 아니라, 청년이 **현재 상태를 이해한 뒤 다음 행동 하나를 고르는** 금융 웹앱으로 보이게 한다. 모든 화면은 먼저 결론을 말하고, 근거는 뒤에 접어 둔다.

화면 설계의 우선순위는 다음과 같다.

1. 지금 상태가 어떤지 한 문장으로 말한다.
2. 지금 필요한 행동을 하나만 강조한다.
3. 판단에 필요한 금액과 상태를 짧게 보여준다.
4. 계산 근거·상세 지표·긴 목록은 접기 영역이나 바텀시트로 옮긴다.

규칙 버전, 계획 버전, 시나리오 ID, 멱등성 키 등 운영 용어는 고객 화면에서 숨기고 `?demo=true` 시연 모드에서만 노출한다.

### 1.0 로고와 상단 바

- 로고는 첨부된 iM금융그룹 심볼에서 착안한 곡선형 초록색 `M` 도형(`ui/BrandMark`)을 사용한다.
- 상단 바 바탕은 흰색이고 서비스명 `iM이룸`은 심볼 옆에 이미지 워드마크와 같은 회색(`#666666`) 굵은 글자로 쓴다. 보조 문구는 짙은 회색, 버튼은 옅은 회색 테두리로 대비를 확보한다.
- 같은 로고 도형을 브라우저 탭 아이콘(`index.html`의 인라인 SVG)과 24개월 적용 예시 화면에도 쓴다.
- 사용자명 아래에는 `(가상 고객)` 같은 꼬리표를 붙이지 않고 `{이름} 님`만 쓴다. 가상 데이터라는 사실은 푸터 고지와 홈의 `데이터와 동의 상태` 영역에서 알린다.

### 1.1 고객 화면 용어

고객 화면에는 개발 용어를 쓰지 않는다. 시연 도구(`?demo=true`)와 소스 주석에서만 사용한다.

| 쓰지 않는 표현 | 고객 화면 표현 |
|---|---|
| Mock API, 서버 세션 | 가상 데이터 기반 체험 |
| fixture, 번들 fixture | 앱에 담아 둔 가상 데이터 |
| contract version, dataset version | (표시하지 않음) |
| backend, 백엔드가 계산한 | (주어 없이 결과만 표시) |
| rule engine, 규칙 엔진 | 같은 조건이면 같은 결과가 나오는 계산 |
| 합성 데이터 | 가상 데이터 |
| 프로토타입 | 체험판 |
| API key, ANTHROPIC_API_KEY, 키 없음 | (표시하지 않음. 출처 칩만 바뀐다) |
| Claude 오류, HTTP 500, Schema 위반 | (표시하지 않음. 준비된 설명으로 대체) |
| JSON, 모델 ID, 프롬프트 | (표시하지 않음) |
| LLM, 생성형 모델 | AI 설명 |
| 데이터 기준일 | 데이터 기준일 (그대로 사용) |
| 새는 돈 (확정 표현) | 확인 후보 |
| 남기는 금액, 생활 유동성, 잔액 | 잔액 |
| 상품 바운더리 | 모으는 방식 |
| (가상 고객) 꼬리표 | (표시하지 않음) |

가상 고객 선택 화면에는 이 단계가 **공모전 체험을 위한 단계**라는 점을 한 줄로 표시한다.

## 2. 정보 구조

- 진입 흐름: **서비스 소개 → 가상 고객 선택 → 모의 데이터 수집 동의 → 3분 재무진단 → 목표 설계 → 재무 홈**
- 기본 진입: **재무 홈** (진단이 끝난 뒤)
- 주요 메뉴(모바일 하단 고정 4개): **홈 / 목표 / 이번 달 / 혜택**
- 보조 메뉴: **재무진단 상세 / 변경 내역 / 서비스 안내 / 동의 철회** — 모바일에서는 홈의 `더 보기` 영역, 데스크톱에서는 상단 탭 오른쪽 그룹에 둔다.
- 적용 예시 모드: `?example=true`에서 최종기획서의 2년 관리 여정을 독립 대시보드로 제공한다.
- 데스크톱: 주요 메뉴 4개를 왼쪽에, 보조 메뉴를 오른쪽에 분리해 한 줄로 제공한다.

### 2.1 재무 홈

정보 순서를 고정한다.

1. **이번 달 상태** — 결론형 문장 한 줄
2. **지금 필요한 행동 하나** — 강조 버튼 1개
3. **가장 중요한 목표** — 1순위 목표의 이번 달 납입액·남은 금액·예상 달성 시점
4. **소득·지출·저축 가능 금액 요약**
5. **새로 확인할 정책 또는 혜택**
6. **더 보기** — 보조 메뉴와 데이터·동의 상태(접기)

결론형 문장은 새로 계산하지 않고 월간 점검 응답의 `routing`, 계획 상태, 상담 케이스 상태와 `reviewNeedsAttention()` 판정을 문구로 옮긴다. 이 매핑은 `api/labels.ts`의 `resolveHomeStatus()` 한 곳에서만 정의한다.

| 상태 | 문장 | 강조 행동 |
|---|---|---|
| 정보성 변화만 있음 | 이번 달 계획은 정상적으로 유지되고 있어요. | 점검 결과 보기 |
| 조정안 대기 | 확인이 필요한 변화가 있어요. | 조정안 확인하기 |
| 승인 후 실행 전 | 조정안을 승인했어요. 모의 실행만 남았어요. | 모의 실행하기 |
| 모의 실행 완료 | 조정안의 모의 실행을 완료했어요. | 변경 내역 보기 |
| 거절 | 기존 계획을 유지하기로 했어요. | 목표 계획 보기 |
| 위험·상담 미완료 | 상담이 필요한 위험 신호가 발견됐어요. | 상담 내용 확인하기 |
| 계획 시작 전 | 목표 계획을 아직 시작하지 않았어요. | 목표 계획 시작하기 |

### 2.2 재무진단 결과

결론을 먼저 쓴다. 예: `매달 865,283원을 저축할 수 있어요.` 값이 `null`이면 계산하지 못했다고 쓰고, 음수면 모자라는 금액으로 쓴다.

들어오는 돈·나가는 돈·비상자금은 세로 요약 줄로 구성한다. 다음 항목은 **분석 근거 보기** 접기 영역으로 옮긴다.

- 분석 기간, 거래 수, 포함된 달, 월평균에 사용한 달
- 데이터 완전성, 결측 월
- 제외한 중복 거래, 제외한 내부 이체
- 월별 흐름, 분류된 거래 목록

새는 돈은 확정 사실이 아니라 **확인 후보**로 표시하고, 정리했을 때의 여력은 추정임을 함께 쓴다.

### 2.2-1 목표 설계 (재무진단 직후)

재무진단이 끝나면 곧바로 홈으로 보내지 않고, 사용자가 자신의 목표를 직접 만드는 단계를 거친다. 한 화면에 질문 하나만 두고 7단계로 나눈다.

| 단계 | 질문 | 입력 |
|---|---|---|
| 1 | 어떤 목표를 모으고 싶나요? | 목표 종류 선택(최대 5개) · 이름 수정 |
| 2 | 얼마를 모을까요? | 목표별 목표 금액 |
| 3 | 언제까지 모을까요? | 목표별 기한(6·12·24·36·60개월 또는 직접 입력) |
| 4 | 이미 모아 둔 돈이 있나요? | 목표별 현재 준비 금액 |
| 5 | 어떤 목표를 먼저 채울까요? | 우선순위(위·아래 버튼) |
| 6 | 어떤 방식으로 모을까요? | 모으는 방식(안정형·균형형·목표집중형) |
| 7 | 이 계획으로 시작할까요? | 계획 미리보기 확인 후 승인 |

규칙:

- 시작값은 그 고객이 이미 가지고 있는 목표이다. 그대로 두고 넘어가면 기존 P01~P03 시나리오와 같은 계획이 나온다.
- 상단에 `추천 목표 그대로 쓰기`를 두어 설계 단계를 건너뛸 수 있게 한다. 건너뛰면 추천 계획으로 홈에 진입한다.
- 진행률(`n / 7`)과 단계 이름을 항상 보여주고, 각 단계에서는 그 단계의 입력만 검사한다. 문제가 있으면 `role="alert"`로 알리고 다음 단계로 넘기지 않는다.
- 금액 입력은 숫자만 받고 천 단위 구분 기호로 보여준다. `+100만원`, `+10만원`, `0으로 지우기` 보조 버튼을 둔다.
- 우선순위는 끌어놓기 대신 위·아래 버튼으로 바꾸고 각 버튼에 `sr-only` 이름을 붙인다.
- 미리보기 금액·달성 시점은 계약 응답 값이다. 입력 단계에서 보여주는 `남는 금액`은 사용자가 방금 입력한 두 값의 차이일 뿐 계획 금액이 아니다.
- 승인은 계획 등록(`검토 대기`)까지만 한다. 확정과 모의 실행은 기존처럼 `나의 목표` 화면에서 이어간다.
- 계획을 시작하기 전에는 `나의 목표` 화면에서 `목표 금액·기한·우선순위 다시 정하기`로 이 단계에 다시 들어올 수 있다. 시작한 계획의 목표는 덮어쓰지 않는다.
- 하단 행동은 모바일에서 고정하고 데스크톱(`md` 이상)에서는 본문 흐름에 둔다. 이 화면에는 하단 내비게이션이 없다.

### 2.3 나의 목표

목표 카드에 먼저 보여줄 값만 둔다.

- 목표 이름, 달성 가능 상태
- 이번 달 납입액, 남은 금액, 예상 달성 시점

다음 값은 **계산 근거와 상세 보기** 바텀시트로 옮긴다.

- 기한 내 달성에 필요한 월 납입액, 부족액, 목표 기한, 예상 소요 기간
- 연결 상품, 배분 근거

한 카드에 `KeyValueRow`를 길게 반복하지 않는다. 카드 본문은 세로 요약 줄 3개를 넘기지 않는다. 계산 전제와 공지는 한 블록(`확인할 점`)에 모으고 여러 개의 강조 카드로 쪼개지 않는다.

목표 목록 다음에는 **달성 방법**(`GoalMethodExplainer`)을 둔다. "계획을 만들었습니다"로 끝내지 않고 목표가 채워지는 과정을 네 단계로 설명한다.

1. 매달 쓰고 남는 돈을 먼저 계산합니다 — 저축 여력
2. 정한 순서대로 목표에 나눕니다 — 월 납입 합계와 잔액
3. 상품 한도와 자격을 확인해 금액을 맞춥니다 — 자동 배분하지 않은 목표 수
4. 매달 다시 점검해 필요하면 조정합니다 — 1순위 목표의 예상 달성 시점

문장에 들어가는 금액·기간은 모두 계획 응답 값이며 화면에서 다시 계산하지 않는다. 이 블록은 강조 카드를 쓰지 않는다. 같은 블록을 목표 설계의 미리보기 단계에서도 쓴다.

예상 달성 시점은 `2027-09`가 아니라 `2027년 9월`로 표시한다(`monthText`).

### 2.4 상품 바운더리 (모으는 방식)

사용자에게는 투자 성향 진단이 아니라 **모으는 방식**으로 설명한다.

| 선택지 | 화면 설명 |
|---|---|
| 안정형 | 예·적금 중심 · 변동 최소화 |
| 균형형 | 목표 기간과 월 부담의 균형 |
| 목표집중형 | 빠른 달성 우선 · 월 납입 부담 증가 |

선택하면 응답 값으로 **월 납입 합계 / 1순위 목표 예상 달성 시점 / 잔액**의 변화를 보여준다. 화면에서 금액을 다시 계산하지 않는다. 계획을 시작한 뒤에는 방식을 바꾸지 않는 기존 정책을 유지한다.

후보 상품은 목표를 고르는 흐름 안에 펼쳐 두지 않는다. `이 방식에서 쓰는 상품 N개 보기` 버튼으로 **바텀시트**에서만 연다. 바텀시트에는 상품명·제공기관·만기·월 납입 한도·금리와 함께 "상품은 계산에 쓰는 후보일 뿐이며 권유가 아니다"라는 고지를 둔다. 제도별 자격까지 보려면 `받을 수 있는 혜택` 화면으로 넘긴다.

### 2.5 이번 달 점검

정보 순서를 고정한다.

0. **다음 달로 넘어가는 과정**(`MonthTransitionPanel`) — 점검 버튼 한 번에 여러 일이 한꺼번에 일어나므로, 무엇 때문에 계획이 달라졌는지 보이도록 과정을 네 단계로 나눠 보여준다.
1. **무엇이 달라졌는지** — 이벤트 2건까지 펼치고 나머지는 접는다.
2. **목표에 어떤 영향이 있는지** — 목표별 월 납입액과 예상 달성 시점의 전후 비교
3. **기존 계획과 조정안 차이** — 월 납입액, 잔액, 기한 내 달성
4. **사용자가 선택할 행동** — 하단 고정 영역

가로 스크롤 표를 쓰지 않는다. 비교는 `월 납입액: 550,000원 → 430,000원`처럼 **세로 비교 줄**로 표시하고, 두 값은 모두 점검 응답에서 읽는다. 지난달·이번 달 지표 비교는 접기 영역에 둔다.

조정안 처리 이후 상태 문구를 다음과 같이 구분한다.

| 상태 | 화면 표시 |
|---|---|
| 대기 | 확인 필요 |
| 승인 후 실행 전 | 실행 필요 |
| 모의 실행 완료 | 처리 완료 / 계획 상태 `모의 실행 완료` |
| 거절 | 기존 계획 유지 / 계획 상태 `거절함` |
| 위험 상담 미완료 | 상담 확인 필요 |

조정안을 거절하면 거절 상태는 비교 화면에 남고, 홈과 목표의 활성 계획은 `review.previousPlan`으로 되돌린다. 거절 동작의 버튼 문구는 `기존 계획 유지하기`로 고정한다.

#### 2.5.1 다음 달 전환 표시

- 어느 달에서 어느 달로 넘어가는지 두 개의 월 칩으로 보여준다. 실행 전에는 오른쪽 칩을 점선 테두리와 `다음 달 · 아직 수집 전`으로 두고, 실행 뒤에 실제 기준일로 채운다.
- 네 단계는 **다음 달 거래 수집 → 지난달과 나란히 비교 → 달라진 점 찾기 → 필요하면 조정안 만들기**로 고정한다.
- 실행 전에는 앞으로 할 일을, 실행 뒤에는 실제로 처리한 값(수집 거래 수, 월평균에 사용한 달 수, 찾은 변화 수, 만든 조정안 버전)을 같은 자리에 쓴다. 건수는 모두 점검 응답 값이다.
- 단계 상태는 아이콘만으로 알리지 않고 `완료 / 진행 중 / 대기 중`을 `sr-only` 텍스트로 함께 제공한다.

## 5. 프로토타입 표시

모든 고객·거래 데이터는 가상 데이터이며 실제 금융 거래가 없음을 푸터와 주요 진입 화면에 표시한다. 실제 마이데이터 연결, 정책 수혜 확정, 가입 완료처럼 오해될 표현을 쓰지 않는다. 자격 정보가 부족하면 충족으로 채우지 않고 `서류 확인 필요`로 표시한다.

## 6. 화면 검수 체크

- 모바일 375px과 데스크톱 1280px에서 **페이지 전체 가로 스크롤 없이** 핵심 기능을 쓸 수 있는가.
- 375px 첫 화면에 이번 달 상태 문장과 주요 행동 버튼이 함께 보이는가.
- 하단 바와 하단 고정 행동 영역이 서로, 그리고 콘텐츠를 가리지 않는가.
- 한 화면에 주요 강조 카드가 1개인가.
- 고정 예시 금액이 현재 fixture·계산 결과와 어긋나지 않는가.
- 고객 화면에 내부 버전·시나리오 제어·개발 용어가 나타나지 않는가.
- 일반 서비스 소개 화면에서 시나리오 주입 동작이 실행되지 않는가.
- 납입액 0원 또는 자격 확인 전 상품이 `999개월`이나 `자격 충족`으로 보이지 않는가.
- 버튼·링크에 키보드 초점이 보이고 상태가 텍스트로 전달되는가.
- 버튼 문구가 잘리지 않는가.
- 목표 설계의 각 단계에서 질문 하나와 입력만 보이는가. 잘못된 값에서 다음 단계로 넘어가지 않는가.
- 목표를 바꾸지 않고 설계를 마치면 기존 P01~P03 계획과 같은 금액이 나오는가.
- 후보 상품이 본문 흐름을 막지 않고 바텀시트에서만 열리는가.

## 8. 상태 표시 규칙

- **로딩**: 단계별 진행 목록과 스켈레톤을 쓰고, 응답이 도착하기 전에는 완료로 표시하지 않는다.
- **빈 상태**: 실행 이력·변화 기록이 없으면 다음 행동 버튼과 함께 빈 상태를 보여준다.
- **오류**: `role="alert"` 영역에 서버 메시지를 그대로 보여주고 재시도 버튼을 제공한다.
- **오프라인**: Mock API 서버에 연결하지 못하면 상단에 `오프라인 체험` 배너를 고정하고 번들 fixture로 계속 진행한다. 배너 문구에는 개발 용어를 쓰지 않는다.
- **결측**: 값이 `null`이면 0으로 채우지 않고 `확인 필요`로 표시한다. 결측 월은 `수집 실패`로 표시한다.
- **명령 결과**: 승인·거절·모의 실행 결과는 `aria-live` 영역에 응답 메시지(중복 무시, 오래된 기준 등)를 그대로 노출한다.
- **계획 미리보기**: 시작 전 계획은 `아직 시작 전`, 시작 후에는 계약의 계획 상태(`검토 대기`·`승인됨`·`모의 실행 완료`·`거절함`)를 표시한다.
- **세션 초기화**: 화면 상태만 지우지 않고 Mock 세션(계획 상태·모의 실행 이력·상담 케이스·동의 철회)까지 초기화를 요청한다. 서버 세션 초기화는 시연 제어 권한이라 `?demo=true`에서만 성공하고, 고객 세션에서는 남아 있는 상태를 그대로 알린다. 오프라인 체험은 브라우저 세션이므로 항상 완전히 초기화된다.
- **되돌릴 수 없는 동작**: 수집 동의 철회는 이 세션에서 되돌릴 수 없으므로 확인 단계를 거치고, 철회 후에는 월간 점검 버튼을 오류 대신 비활성 상태와 사유로 보여준다. 같은 세션에서 동의를 임의로 재활성화하지 않는다.

## 9. AI 설명과 AI 가이드

AI는 계산하지 않는다. 문장만 만든다. 금액·자격·기간은 계약 응답의 값을 그대로 표시하고 화면에서 다시 계산하지 않는다.

### 9.1 화면 위치

| 화면 | 요소 | 내용 |
|---|---|---|
| 이번 달 점검 | `AiExplanationPanel` | 점검 결과를 쉬운 문장으로 설명. `무엇이 달라졌나요` 다음, `목표에 어떤 영향이 있나요` 앞에 둔다. |
| AI 가이드(상단 바) | `AiCounselPanel` | 내 상태에 대해 질문하고 답변을 받는다. |
| AI 가이드(상단 바) | `계산 근거 바로 보기` | 기존 규칙 기반 근거 목록. `규칙 기반 설명` 칩을 유지한다. |

설명 패널은 강조 카드를 쓰지 않는다. 한 화면의 주요 강조 카드는 결론형 상태 카드(`HeadlineCard`) 1개라는 규칙을 유지하고, 설명은 중립 배경 카드로 둔다.

### 9.2 출처 표시

설명이 어떤 경로로 만들어졌는지 항상 표시한다. 문구는 `api/labels.ts`의 `AI_SOURCE_LABEL` 한 곳에서만 정의한다.

| 응답의 `source` | 칩 문구 | 톤 | 보조 설명 |
|---|---|---|---|
| `CLAUDE` | Claude가 생성한 설명 | positive | 계산 결과를 바탕으로 이번에 새로 작성한 설명입니다. |
| `FIXTURE` | 미리 준비된 AI 설명 | neutral | 앱에 담아 둔 설명으로 안내하고 있습니다. 금액과 목표 상태는 계산 결과와 같습니다. |
| `RULE` | 규칙 기반 설명 | muted | 계산 결과를 정해진 문장 형식으로 그대로 옮긴 설명입니다. |

출처 칩 아래에는 항상 **데이터 기준일**과 **가상 데이터·비추천 고지**를 함께 둔다. 내부 모델 ID는 응답 `metadata.model`에만 두고 화면에 노출하지 않는다.

상담 답변에는 근거마다 **출처명과 기준일**을 표시한다. 공식 URL이 있으면 `출처 보기` 링크를 새 탭으로 연다.

### 9.3 상태 표시

- **로딩**: `설명을 준비하고 있습니다.` / `답변을 준비하고 있습니다.` 와 스켈레톤을 쓴다. `aria-busy`와 `aria-live`를 둔다. 응답 전에는 완료 문구를 보여주지 않는다.
- **재시도**: 설명에는 `설명 다시 받기`, 답변에는 `답변 다시 받기` 버튼을 둔다.
- **상담사 연결**: 위험 분류나 상담 사유가 있으면 `상담사 연결이 필요해요` 안내를 설명과 답변 모두에 표시한다. 이 판정은 규칙 엔진 결과를 따르며 모델 판단으로 덮지 않는다.
- **오류**: 고객 화면에는 개발자용 오류를 쓰지 않는다. 호출이 실패하면 오류 메시지 대신 같은 계약의 준비된 설명 또는 규칙 기반 설명을 보여주고 출처 칩만 바뀐다. `API 키가 없습니다`, `HTTP 500`, `Claude 오류` 같은 문구는 화면에 나오지 않는다.
- **데이터 없음**: 진단 결과가 없으면 `설명할 데이터가 아직 없습니다.`로 표시하고 빈 카드를 성공 화면처럼 보여주지 않는다.

### 9.4 상담 질문 범위

질문 예시 버튼으로 답할 수 있는 범위를 먼저 보여준다: 납입액이 달라진 이유, 영향받은 목표, 거절했을 때의 결과, 확인할 수 있는 지원제도, 상담사 연결이 필요한 이유. 자유 입력은 300자로 제한한다.

범위를 벗어난 질문에는 `현재 데이터만으로 확인하기 어렵습니다`로 답하고 확인할 수 있는 화면을 안내한다. 수익률·대출 승인 가능성·지원 대상 확정은 답하지 않는다.

### 9.5 개인정보 표시

AI 가이드 진입 문구에 이름·계좌번호 같은 개인정보를 쓰지 않는다는 점을 한 줄로 밝힌다. 화면에 표시되는 설명에도 고객 이름을 쓰지 않는다.

## 10. 접근성

- 터치 영역 최소 44×44px.
- 키보드 초점 표시(`:focus-visible`)를 모든 조작 요소에서 유지한다.
- 아이콘만 있는 버튼에는 `sr-only` 이름을 제공한다.
- 상태를 색만으로 구분하지 않고 아이콘과 텍스트 라벨을 함께 쓴다.
- 모달과 바텀시트는 열릴 때 초점을 옮기고, `Tab` 순환을 가두며, 닫히면 호출한 버튼으로 초점을 되돌린다. `onClose`처럼 매 렌더 새로 만들어지는 함수는 효과 의존성에 넣지 않는다(초점 복원 대상이 사라진다).
- 본문 최소 글자 크기는 14px를 권장하고, 긴 문장에는 `leading-relaxed`와 `break-keep`을 적용한다.
- 375px에서 페이지 전체 가로 스크롤을 만들지 않는다. 표가 필요한 경우 세로 비교 줄로 바꾼다.
- 하단 고정 요소에는 `env(safe-area-inset-bottom)`을 반영한다.
- 상태 변경 결과(처리 결과, 이번 달 상태)는 `aria-live` 영역에 둔다.
- 단계·필터 선택 버튼에는 `aria-pressed`를 유지한다.

### 10.1 24개월 적용 예시 시점 선택

`?example=true`의 7개 시점(가입 · 1 · 7 · 11 · 15 · 21 · 24개월)은 가로 스크롤로 숨기지 않고 모바일 4열 / 데스크톱 7열 그리드로 모두 노출한다. `aria-pressed`, 키보드 선택, 44px 터치 영역, 선택 시 `선택함` 스크린리더 텍스트를 유지한다. 시점을 바꾸면 설명·주요 금액·월 관리 금액·목표별 배분·세부 근거·보증금 진행률이 함께 갱신된다.
