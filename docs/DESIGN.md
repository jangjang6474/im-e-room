# iM 이룸 — UI 디자인 기준

최종 갱신: 2026-09-20

## 1. 제품 인상

iM 이룸은 내부 계산 과정을 전시하는 대시보드보다 청년이 매달 목표를 확인하고 다음 행동을 고르는 금융 웹앱으로 보이게 한다. 첫 화면은 현재 목표, 이번 달 변화, 실행 가능한 다음 행동을 우선한다. 규칙 버전, 계획 버전, 시나리오 ID, 멱등성 키 등 운영 용어는 고객 화면에서 숨기고 `?demo=true` 시연 모드에서만 노출한다.

## 2. 정보 구조

- 진입 흐름: **서비스 소개 → 가상 고객 선택 → 모의 데이터 수집 동의 → 3분 재무진단 → 재무 홈**
- 기본 진입: **재무 홈** (진단이 끝난 뒤)
- 주요 메뉴: **홈 / 나의 목표 / 이번 달 점검 / 받을 수 있는 혜택**
- 보조 메뉴: **재무진단 / 변경 내역 / 서비스 소개 / AI 가이드**
- 적용 예시 모드: `?example=true`에서 최종기획서의 2년 관리 여정을 독립 대시보드로 제공한다.
- 모바일: 주요 메뉴 4개를 화면 하단 고정 바로 제공한다. 보조 메뉴는 홈 카드의 이동 버튼으로 연결한다.
- 데스크톱: 주요 메뉴와 보조 메뉴를 상단 탭 한 줄에서 제공한다.

재무 홈의 우선순위는 ① 목표 진행률 ② 이번 달 확인할 변화 ③ 소득·지출·저축 가능 금액 ④ 목표별 납입 계획 ⑤ 지원제도 상태이다.

3분 재무진단 화면에는 최근 거래의 실제 분석 기간과 거래 수를 표시한다. 급여·고정·변동·비정기 지출을 구분하고, 새는 돈은 `후보`로 표시해 사용자가 미사용 구독이나 리볼빙 이자 여부를 확인하게 한다. `최근 12개월`처럼 고정된 기간을 화면 문구로 사용하지 않는다.

## 3. 시각 언어

| 용도 | 값 |
|---|---|
| 주색 | `#00C4A6` |
| 짙은 민트 | `#006B5B` |
| 본문 | `#142B29` |
| 보조 글자 | `#526562` |
| 캔버스 | `#F6F9F8` |
| 경계선 | `#DCE7E4` |
| 민트 패널 | `#EAFBF6` |
| 하늘 패널 | `#EEF5FF` |
| 라임 패널 | `#F6FADC` |
| 라벤더 패널 | `#F5EFFF` |

- 기본 본문은 16px, 보조 설명은 14px, 상태·메타 정보는 12px을 권장한다.
- 금융 금액에는 tabular numbers를 사용한다.
- 패널은 16~24px 모서리와 얕은 그림자를 사용한다.
- 상태는 색만으로 구분하지 않고 `이용 가능`, `서류 확인 필요`, `현재 대상 아님`처럼 텍스트를 함께 표시한다.

## 4. 상호작용

- 주요 터치 영역은 최소 44px, 모바일 하단 메뉴는 56px 이상으로 한다.
- 계획 변경은 변경 이유와 전후 금액을 보여준 다음 사용자가 승인하게 한다.
- 승인 전에는 기존 계획이 유지된다는 점을 명시한다.
- 데이터 기준일, 다음 월간 점검일, 합성 데이터 사용 여부를 화면에서 확인할 수 있어야 한다.
- 키보드 초점 표시와 `prefers-reduced-motion`을 지원한다.
- 모바일 콘텐츠에는 하단 고정 바와 기기 safe area만큼의 여백을 둔다.

## 5. 프로토타입 표시

모든 고객·거래 데이터는 합성 데이터이며 실제 금융 거래가 없음을 푸터와 주요 진입 화면에 표시한다. 실제 마이데이터 연결, 정책 수혜 확정, 가입 완료처럼 오해될 표현을 쓰지 않는다. 자격 정보가 부족하면 충족으로 채우지 않고 `서류 확인 필요`로 표시한다.

## 6. 화면 검수 체크

- 모바일 375px과 데스크톱 1280px에서 가로 스크롤 없이 핵심 기능을 쓸 수 있는가.
- 하단 바가 콘텐츠와 버튼을 가리지 않는가.
- 고정 예시 금액이 현재 fixture·계산 결과와 어긋나지 않는가.
- 고객 화면에 내부 버전이나 시나리오 제어가 나타나지 않는가.
- 일반 서비스 소개 화면에서 시나리오 주입 동작이 실행되지 않는가.
- 납입액 0원 또는 자격 확인 전 상품이 `999개월`이나 `자격 충족`으로 보이지 않는가.
- 버튼·링크에 키보드 초점이 보이고 상태가 텍스트로 전달되는가.


## 7. 화면과 Mock 계약 연결

고객 화면은 `frontend/src/api/`의 세션 상태를 통해 Mock 계약(`/api/mock`, 실패 시 같은 계약의 번들 fixture)을 소비한다.
컴포넌트는 금액·자격·변화 판정을 다시 계산하지 않고 응답 필드를 그대로 표시한다.

| 화면 | 컴포넌트 | 사용하는 계약 |
|---|---|---|
| 서비스 소개 | `ServiceIntroView` | `GET /personas` (고객 수 표시) |
| 가상 고객 선택 | `PersonaSelectView` | `GET /personas` |
| 모의 수집 동의 | `ConsentView` | 동의 기록(클라이언트) · 기준일은 페르소나 응답 |
| 3분 재무진단 진행 | `DiagnosisProgressView` | 진단·자격·상품·계획 호출 진행 단계 |
| 재무 홈 | `tabs/HomeTab` | `diagnosis`, `eligibility`, `plan`, `monthly-review` |
| 재무진단 상세 | `tabs/DiagnosticsTab` | `GET /personas/:id/diagnosis` |
| 나의 목표 | `tabs/GoalsTab` | `GET /plan/preview`, `POST /plans`, `POST /plans/:id/approve·execute`, `GET /products` |
| 이번 달 점검 | `tabs/MonthlyReviewTab` | `POST /personas/:id/monthly-review`, 승인·거절 명령 |
| 받을 수 있는 혜택 | `tabs/PolicyCenterTab` | `GET /eligibility`, `GET /products` |
| 변경 내역 | `tabs/ExecutionHistoryTab` | `GET /executions`, 계획 상태, 감지된 이벤트 |
| 상담사 대기 목록(`?demo=true`) | `ConsultantView` | `GET /consultations` |
| 24개월 적용 예시(`?example=true`) | `ExampleJourneyDashboard` | `GET /example-journey` |

## 8. 상태 표시 규칙

- **로딩**: 단계별 진행 목록과 스켈레톤을 쓰고, 응답이 도착하기 전에는 완료로 표시하지 않는다.
- **빈 상태**: 실행 이력·변화 기록이 없으면 다음 행동 버튼과 함께 빈 상태를 보여준다.
- **오류**: `role="alert"` 영역에 백엔드 메시지를 그대로 보여주고 재시도 버튼을 제공한다.
- **오프라인**: Mock API 서버에 연결하지 못하면 상단에 `오프라인 체험` 배너를 고정하고 번들 fixture로 계속 진행한다.
- **결측**: 값이 `null`이면 0으로 채우지 않고 `확인 필요`로 표시한다. 결측 월은 표에서 `수집 실패`로 표시한다.
- **명령 결과**: 승인·거절·모의 실행 결과는 `aria-live` 영역에 백엔드 메시지(중복 무시, 오래된 기준 등)를 그대로 노출한다.
- **계획 미리보기**: 등록 전 계획은 `미리보기`, 등록 후에는 계약의 계획 상태(`검토 대기`·`승인됨`·`모의 실행 완료`·`거절함`)를 표시한다.
- **세션 초기화**: 화면 상태만 지우지 않고 Mock 세션(계획 상태·모의 실행 이력·상담 케이스·동의 철회)까지 초기화를 요청한다. 서버 세션 초기화는 시연 제어 권한이라 `?demo=true`에서만 성공하고, 고객 세션에서는 남아 있는 상태를 그대로 알린다. 오프라인 체험은 브라우저 세션이므로 항상 완전히 초기화된다.
- **되돌릴 수 없는 동작**: 수집 동의 철회는 이 세션에서 되돌릴 수 없으므로 확인 단계를 거치고, 철회 후에는 월간 점검 버튼을 오류 대신 비활성 상태와 사유로 보여준다.

## 9. AI 가이드

외부 API 키 없이 동작해야 하므로 고객 화면의 AI 가이드는 생성형 모델을 호출하지 않는다.
계획 전제·공지·배분 사유, 분석 기간 메모, 자격 미확인 요건, 감지된 이벤트 메시지처럼 백엔드가 이미 계산한 근거만 모아 보여주고 `규칙 기반 설명`으로 표시한다.
