# iM 이룸 — PRD

버전: 0.1 · 작성일: 2026-09-19 · 상태: 공모전 프로토타입 구현용 초안

## 1. 문서 기준

기준 자료는 `완성되어가는중.hwpx`와 기획 대화이다. 원본 제안서는 수정하지 않는다. 서로 다른 내용은 최근 사용자 결정에 맞춰 정리했다.

| 구분 | 기준 |
|---|---|
| 확정된 방향 | 서비스명 iM 이룸, 청년 목표 중심 재무관리, 상황 변화에 따른 계획 재설계 |
| 프로토타입 전제 | 실제 마이데이터를 사용하지 않고 API 응답 구조를 참고한 완전 합성 데이터로 재현 |
| 고객 데이터 수집 | 모의 동의 시점을 기준으로 최초 수집 후 매월 1회 수집 |
| AI 역할 | 정책 요건 구조화 보조, 계산 결과 설명, 근거 문서 기반 질의응답 |
| 임시 설정 | 감지 임계값, 배분 비율, 비상자금 기준, 상품별 한도, 성능 목표 |
| 본 문서의 제안 | MVP 우선순위, 화면 구성, 수용 기준 및 측정 방식은 구현을 위한 제안이며 사용자 승인 완료를 의미하지 않음 |

원본의 ‘재무 상태를 매일 확인’은 고객 데이터 월간 수집으로 정리한다. 외부 정책·상품 변경 확인은 별도 흐름이다. 실제 은행 앱 입점·업무 제휴·API 사용 권한이 확보되었다고 가정하지 않는다.

## 2. 제품 정의

**iM 이룸은 청년의 재무 목표를 설정하고, 매월 달라진 상황을 반영해 실행 가능한 저축 계획을 다시 제안하는 서비스이다.**

진단 → 목표 설정 → 자금 배분 → 월간 점검 → 변화 판단 → 계획 재설계 → 사용자 확인 → 결과 저장의 관리 순환을 제공한다. 이 문서에서 포트폴리오는 비상자금·예적금·청약 등 목표별 자금 배분을 뜻한다.

### 문제와 대상

- 1차 대상: 대구 거주 만 19~34세 사회초년생. 서비스 타깃 연령과 개별 정책의 자격 연령은 별개로 관리한다.
- 월 소득은 있지만 고정·비정기 지출을 고려한 저축 여력을 파악하기 어렵다.
- 정책과 상품을 알아도 개인 목표에 맞춰 얼마씩 배분할지 결정하기 어렵다.
- 급여·지출·거주지·상품 조건이 바뀌면 기존 계획을 다시 조정해야 한다.
- 위험 상황에서는 자동 설명을 넘어 사람의 상담이 필요하다.

### 이해관계자 가치 가설

| 대상 | 기대 가치 | 검증 방법 |
|---|---|---|
| 청년 | 이해할 수 있고 유지 가능한 목표별 계획 | 과업 성공률, 설명 이해도, 계획 유지율 |
| 은행 | 청년과의 장기적인 재무관리 접점 | 동의 기반 지속 이용률, 목표별 유지율 |
| 상담사 | 상담 전 상황 파악 시간 감소 | 동일 사례의 브리핑 유무별 준비 시간 비교 |
| 정책 운영기관 | 지원 대상의 제도 발견·신청 지원 | 적격 제도 발견률, 후속 단계별 전환율 |

은행의 의도와 사업 효과는 기획 가설이다. 제안서의 외부 통계는 본 서비스의 효과나 인과관계를 입증한 결과로 사용하지 않는다.

## 3. 범위

### P0: 시연에서 완결할 흐름

1. 가상 고객 선택과 모의 수집 동의·철회.
2. 최초 수집 및 최근 12개월 가상 거래 기반 진단.
3. 목표 금액·기한·우선순위 입력, 최초 계획 산출.
4. 다음 월로 시간 이동하여 재수집·전월 비교.
5. 정보 / 조정 / 위험 이벤트 분류.
6. 지원제도 자격 재확인, 계획 재산출, 변경 전후 비교.
7. 사용자 승인·거절 및 모의 실행 결과 저장.
8. 위험 사례의 상담 대기 목록과 근거 브리핑 표시.
9. 계산 근거와 문서 출처를 활용한 설명 생성. 실패 시 정형 설명 제공.

### P1: 확장 기능

- 정책 원문의 LLM 구조화 초안 및 검수 화면.
- 출처를 표시하는 제한된 정책·상품 Q&A.
- 정책 버전 변경 시 영향받는 가상 고객 재평가.
- 목표 달성 후 다음 목표 제안, 중도해지 대안 비교 화면.
- 학습·평가 데이터가 확보된 거래 분류 모델.

### 프로토타입 제외 범위

실제 계좌 연결, 실제 개인정보·신용정보 수집, 실명 인증, 은행 계정계 호출, 실제 가입·송금·자동이체, 실제 상담 예약·외부 기관 전송, 대출 심사, 투자 매매, 실제 정책 수혜 확정은 구현하지 않는다. 해당 단계는 데모 화면과 모의 응답으로 표현한다. 실서비스 전환 요건은 별도 검토 대상으로 남긴다.

## 4. 주요 사용자 흐름

| 단계 | 사용자 경험 | 시스템 결과 |
|---|---|---|
| 시작 | 데모임을 확인하고 가상 고객 선택 | 시나리오 세션 생성 |
| 동의 | 모의 수집 범위·주기 확인 | 동의 상태와 월간 기준일 저장 |
| 진단 | 소득·지출·부채·저축 여력 확인 | 기준 재무 스냅샷 저장 |
| 설계 | 목표와 기한 입력 | 가능 여부, 월 납입안, 부족분 제시 |
| 점검 | 다음 월 데이터로 변화 확인 | 새 스냅샷 및 근거 이벤트 생성 |
| 재설계 | 기존안과 조정안을 비교 | 승인 대기 계획 버전 생성 |
| 확인 | 승인 또는 거절 | 승인 시에만 모의 실행, 거절 시 기존안 유지 |
| 상담 | 위험 이유와 상담 안내 확인 | 모의 상담 케이스 및 브리핑 생성 |
| 피드백 | 실행·선택 이력 확인 | 다음 점검의 기준 갱신 |

동의 철회 이후 신규 수집을 중단한다. 월간 수집 사이에 실제 고객 상태가 계속 갱신되는 것처럼 표시하지 않는다. 외부 조건 변화나 앱 입력에 따른 판단에는 마지막 고객 데이터 기준일을 함께 표시한다.

## 5. 기능 요구사항과 수용 기준

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-01 | 합성 데이터 제공 | 모든 고객 데이터에 데모 표시, 실사용자 정보 입력·연결 불필요 |
| FR-02 | 월간 스케줄 | 최초 수집 후 동의일 기준 다음 달 실행일 표시; 월말·철회·재시도 처리 |
| FR-03 | 재무진단 | 거래 중복 및 계좌 간 이체로 소득·지출을 이중 집계하지 않음; 누락은 미확인 표시 |
| FR-04 | 목표 설계 | 납입 합계가 가용 여력을 넘지 않음; 달성 불가능하면 부족 금액 또는 기간 조정안 표시 |
| FR-05 | 자격 확인 | 충족·확인 필요·미충족 구분; 알 수 없는 정보를 충족으로 간주하지 않음 |
| FR-06 | 변화 감지 | 이전·현재 값, 데이터 기준일, 적용 규칙 버전을 함께 저장 |
| FR-07 | 이벤트 분류 | 정보는 리포트, 조정은 재설계, 위험은 상담 대기; 복합 이벤트에서 위험 표시 유지 |
| FR-08 | 재설계 | 기존안·조정안의 월 납입액, 예상 달성 시점, 가정과 차이 표시 |
| FR-09 | 설명 | 금액·기간은 계산 결과와 일치; 출처가 없는 정책 사실을 단정하지 않음 |
| FR-10 | 승인·모의 실행 | 승인한 계획 버전에 대해서만 실행; 중복 클릭으로 중복 실행되지 않음 |
| FR-11 | 상담 브리핑 | 위험 근거, 현재 상태, 사용자 목표, 변경 이력 표시; 실제 기관 전송 없음 |
| FR-12 | 피드백 | 수락·거절·실패·완료를 구분해 저장; 승인만으로 실제 저축 성과를 기록하지 않음 |

## 6. 화면

일반 접속의 기본 화면은 재무 홈이다. 모바일 웹앱은 홈·나의 목표·이번 달 점검·혜택을 하단 고정 내비게이션으로 제공하고, 데스크톱은 같은 구조를 상단 내비게이션으로 제공한다. 서비스 소개와 시나리오 제어는 고객의 일상 동선에서 분리한다.

- **시작·동의:** 가상 고객, 시나리오 설명, 수집 범위, 최초·다음 수집일.
- **재무 홈:** 데이터 기준일, 소득·지출·저축 여력, 목표 진행률, 이번 달 변화.
- **목표·최초 계획:** 목표 설정, 배분안, 제약조건, 달성 가능성.
- **변화·계획 비교:** 변화 근거, 전후 수치, 설명, 승인·거절.
- **정책 상세:** 충족 여부와 미확인 항목, 출처·기준일, 신청 안내의 모의 상태.
- **상담 대시보드:** 위험 순 목록, 사례 브리핑, 상담 결과 기록.
- **데모 제어:** 시나리오 선택, 다음 월, 외부 변경 주입, 실패 재현, 초기화.

색상만으로 상태를 구분하지 않고 텍스트 라벨을 병기한다. ‘가입 완료’ 대신 ‘모의 가입 완료’를 표시한다.

## 7. 검증과 KPI

아래 목표는 **프로토타입 품질을 위한 제안 기준**이다. 검증된 업계 기준이나 서비스 효과 예측치가 아니다.

| 지표 | 산식·평가 방법 | 제안 기준 |
|---|---|---|
| 계산 정확성 | 정답 금액·기간과 일치한 테스트 / 전체 계산 테스트 | 필수 사례 100% |
| 제약 위반 | 여력·한도·중복 조건을 위반한 산출안 수 | 고정 검증 세트에서 0건 |
| 승인 통제 | 승인 없이 실행된 건수 | 0건 |
| 동의 철회 통제 | 철회 후 시작된 신규 수집 건수 | 0건 |
| 설명 수치 일치 | 계산 결과와 일치하는 설명 수치 / 설명 내 검증 대상 수치 | 필수 사례 100% |
| 변화 감지 | 유형별 정밀도·재현율; TP·FP·FN도 보고 | 첫 평가 후 기준 확정 |
| 위험 라우팅 | 위험으로 라벨링한 필수 사례 중 상담 대기 생성 비율 | 필수 사례 100% |
| 사용자 이해도 | 변경 이유·납입액·승인 효과를 정확히 답한 비율 | 파일럿 기준선 수집 후 확정 |

정답 데이터는 시나리오 작성자가 규칙 구현과 별도로 검토한다. 임계값 조정용 세트와 최종 평가 세트를 분리한다. 사례 수와 유형별 분포를 공개하여 작은 표본의 100%를 일반화하지 않는다.

운영 단계의 연구 지표는 순자산 변화, 상품 만기 유지율, 지원제도 실제 수혜 건수, 리볼빙·카드론 잔액 변화이다. 각각 기준시점·관찰기간·중도탈락·소득 변화의 영향을 정의한 후 평가한다. 순자산이 0 이하인 고객에게 단순 증가율을 적용하지 않고 절대금액 변화도 보고한다. 합성 데이터로 재무 개선 효과를 입증했다고 주장하지 않는다.

## 8. 완료 기준과 미결정 사항

완료는 정상 월간 점검, 급여 변화, 소득 단절, 정책 변경, 목표 달성 불가, 동의 철회, 실행 재시도 사례를 처음부터 끝까지 재현할 수 있는 상태이다. 같은 입력과 버전에서 계산 결과가 재현되어야 한다.

미결정: 사용할 표준 API 문서 버전, 상품·정책 샘플 목록, LLM 공급자, 최종 UI, 감지 임계값, 배분 우선순위의 사용자 조정 범위, 공모전 제출·평가 세부 조건.
